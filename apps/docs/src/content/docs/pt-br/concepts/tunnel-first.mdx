Esta página explica o transporte tunnel-first do Gambi: por que quem abre a conexão é o participante, e não o hub.

## O formato antigo

Uma versão anterior do Gambi tratava cada participante como um pequeno servidor HTTP:

1. O participante rodava um provedor local (Ollama, LM Studio etc.).
2. Ele avisava o hub: "meu endpoint está acessível em `http://host:port`".
3. O hub roteava cada requisição de inferência fazendo uma chamada HTTP de volta para esse endereço.

Isso funcionava em uma LAN simples, mas empurrava várias restrições para o participante:

- o participante precisava ser acessível a partir do hub
- NAT, isolamento de Wi-Fi e split tunneling de VPN muitas vezes bloqueavam esse caminho
- o participante precisava expor uma porta, o que é pedir muito de um colega com um notebook
- o hub precisava reescrever ou confiar em endereços de provedor que nunca foram dele

O resultado era um sistema que exigia simetria de rede onde ela não existia.

## O formato tunnel-first

Agora o Gambi inverte a conexão. O participante abre um WebSocket até o hub. As requisições de inferência trafegam por esse túnel.

```mermaid title="As duas conexões apontam para o hub. O provedor fica em localhost."
flowchart LR
  app["Seu app"]
  hub(("Hub")):::hub
  subgraph machine["Máquina do participante"]
    rt["Runtime do participante"]
    prov[("Provedor local<br/>Ollama, LM Studio, vLLM")]:::model
  end
  app -->|HTTP| hub
  rt ==>|abre WebSocket| hub
  rt -->|HTTP em localhost| prov
  classDef hub stroke-width:1px
  classDef model stroke-width:1.5px
```

O que muda:

- o hub nunca inicia uma conexão com o participante
- o participante pode manter o endpoint do provedor em `localhost`
- os headers de autenticação ficam no runtime do participante
- o hub roteia por `participant-id`, nome de modelo, `model:<name>` ou `*`, e encaminha a requisição pelo túnel que o participante já abriu

Participantes de harness usam a mesma direção de conexão. O processo do harness fica local e envia mensagens e artefatos pelo túnel aberto pelo participante. Um cliente de harness faz attach nesse participante pelo hub, com um stream de eventos e requisições HTTP comuns. O hub só repassa dados entre conexões que ele não originou. Participantes de harness não são candidatos ao roteamento de inferência.

## O relay ACP opaco

```mermaid title="O hub repassa mensagens ACP entre duas conexões que ele não abriu."
flowchart LR
  client["Cliente de harness<br/>ou app"]
  hub(("Hub")):::hub
  subgraph machine["Máquina do participante"]
    rt["Runtime do participante"]
    acp["Harness<br/>processo ACP v1"]:::harness
  end
  client ==>|HTTP e SSE| hub
  rt ==>|túnel do participante| hub
  rt <-->|stdio| acp
  classDef hub stroke-width:1px
  classDef harness stroke-width:1.5px
```

Cada mensagem ACP viaja com um `sessionId`. O hub confere esse par e depois encaminha a mensagem sem ler o método nem os parâmetros do JSON-RPC ACP. Abrir e fechar uma sessão de harness passam pelo mesmo relay. Os artefatos do workspace sobem como snapshots separados e versionados.

O login local do harness nunca entra no registro do participante, nos eventos de ciclo de vida nem no túnel. Isso é diferente dos artefatos do workspace, que o participante envia de propósito para que um app conectado possa usar a saída do harness.

## O que você ganha

- **Localhost continua sendo localhost.** A URL do provedor que você passa para `gambi participant join` ou `createParticipantSession()` pode ser `http://localhost:11434`, mesmo quando o hub roda em outra máquina. O hub nunca precisa alcançar esse endereço.
- **As credenciais ficam locais.** `authHeaders` e chaves de API só saem do runtime do participante quando o próprio runtime chama o provedor, nunca pelo hub.
- **Menos pré-requisitos de rede para os participantes.** Um participante precisa de conectividade de saída até o hub e nada mais. Sem redirecionamento de porta, sem anúncio por mDNS, sem exceções no firewall.
- **Registro seguro para repetir.** O registro de participante é idempotente, e o bootstrap token do túnel é de uso único. Reiniciar um participante com o mesmo ID é seguro.
- **Reconexão.** Quando o túnel cai, o runtime do participante se registra de novo e reabre o túnel com o mesmo ID de participante. Ele espera 1 segundo e dobra a espera até 30. Apps que roteiam para ele pelo ID mantêm o destino.
- **Cancelamento.** Quando um app abandona uma requisição, o hub cancela a chamada no túnel e o runtime aborta a requisição ao provedor. Assim, a máquina de ninguém continua gerando à toa.

## Do que você abre mão

- **O upgrade para WebSocket precisa passar.** Qualquer proxy entre o participante e o hub precisa encaminhar `Upgrade: websocket`. Alguns proxies corporativos bloqueiam isso.
- **Uma direção, não duas.** O participante precisa alcançar o hub. O hub não precisa alcançar o participante, mas nada passa se a saída estiver bloqueada.
- **A mesma minor nas duas pontas.** O túnel fala o formato de rede da biblioteca de RPC sobre a qual o Gambi é construído, e esse formato pode mudar entre minors. Um hub recusa no registro um participante de outra minor e informa a versão esperada.
- **Requisições em andamento não sobrevivem a uma queda.** Uma requisição que o participante estava respondendo quando o túnel caiu falha com `participant_disconnected`. O runtime volta para a próxima.
- **Um hub reiniciado esquece as salas.** As salas vivem na memória do hub. Um participante que tenta voltar a um hub reiniciado ouve que a sala não existe e para (`left` com `reason: "refused"`). Crie a sala de novo e entre outra vez.
- **Remoção entre tentativas de reconexão.** `participant leave` fecha o túnel de um runtime conectado com `4002`, e o runtime termina. Se alguém o remover durante a espera entre tentativas, não há túnel para receber o código de fechamento. O registro seguinte o traz de volta à sala.

## Garantias

O túnel é o único transporte que o hub usa para alcançar os participantes. Isso traz duas garantias:

1. O status de um participante vem só do túnel dele. Se o túnel não está aberto, o participante está `offline` e não está disponível. Nada de DNS desatualizado, nada de sockets meio abertos fingindo estar vivos.
2. Se uma requisição aponta para um participante cujo túnel não está aberto, o hub responde na hora com HTTP `503` e o código `participant_offline` em vez de esperar um timeout.

Clientes de harness conectados não dependem do túnel do participante. Se o túnel do participante cai e volta, os streams de attach existentes continuam abertos, recebem `harness.disconnected` e depois `harness.connected`, e o repasse é retomado. Uma mensagem que um cliente envia enquanto não há túnel aberto é recusada com `PARTICIPANT_UNREACHABLE`.
